# asar 完整性校验实验矩阵

目标：搞清楚 Typora 1.12.1 到底校验什么，能否通过改程序来修 bug。

## 实验矩阵

| 实验 | 改动 | 结果 | 结论 |
| --- | --- | --- | --- |
| A | 原始 asar，直接跑 | 正常启动 | 基线 |
| C | 头完全不动，原地改 `package.json` 一个字节 | 正常启动 | **文件内容不校验** |
| E | 改 `launch.dist.js` + 新增一个文件 + 同步更新清单 | `ERROR [LC] l` / `ERROR Integrity check failed`，进程退出 | **头/清单不能动** |
| F | 头不动，`launch.dist.js` 同长度换两个引号 | 未定论 | 测试被日志轮转污染，结果不可信 |

C 和 E 的对比是整件事的关键：**校验的是清单，不是内容**。

## asar 容器格式

```text
uint32(4)      前 4 字节（固定值）
uint32(4)      headerLen   JSON 头的字节数
uint32(4)      payloadLen  数据区总字节数
uint32(4)      jsonLen     JSON 字符串字节数
json           headerLen 字节的 JSON
pad4           补 0 到 4 字节对齐
data           payloadLen 字节的文件数据
```

原始文件的 **data 起始偏移 = 800**。

> 踩过的坑：第一次按 797 解包，解出来的 `launch.dist.js` 末尾少了 3 个字节，
> 语句断在半截。正确值是 800（4 字节对齐）。

## 清单条目结构

```json
{
  "files": {
    "launch.dist.js": {
      "size": 1383,
      "offset": "379120",
      "integrity": {
        "algorithm": "SHA256",
        "hash": "3ec9df88...",
        "blockSize": 4194304,
        "blocks": ["3ec9df88..."]
      }
    }
  }
}
```

`offset` 是**字符串**，不是数字。这是 asar 格式的一个常见陷阱 —— 用数字写回去会解析失败。

## 一个有意思的矛盾

头里声明的 jsc hash：

```text
2f69400a06c3b199e13ce8ab82914c0bdd3340e1bbcc76ee1cddc0ebf4cd6d35
```

而文件实际的 SHA256：

```text
9941c26e782f0bf77549fd6cc07999431101925e90f661e152072da3455ef822
```

**两者不一致，但程序正常启动。**

这说明校验不是全量的，或者对该条目有豁免。无论哪种，都意味着：
"校验失败"并不是简单的"内容变了"就触发，具体触发条件还没完全摸清。

## 重建实验

把 3 个原始文件重新打包，得到的头与原始文件**逐字节一致**，
唯一差异就是上面那个 jsc hash 字段。

这证明"逐字节重建原始 asar"在技术上是可行的，
只是没有意义 —— 因为要修 bug 就必须改内容，而改内容就动不了头。

## 结论

想通过改程序修这个 bug，可行空间只有：

- 头（含清单）**保持逐字节不变**
- 文件内容**长度不变**
- 原地替换字节

`launch.dist.js` 只有 1383 字节，要在里面塞进判空逻辑，空间极其紧张。
这条路性价比很低 —— 所以最终选择了不改程序的外部方案。
